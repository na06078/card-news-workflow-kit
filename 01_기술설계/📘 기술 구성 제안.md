## 2. 언어와 웹 구성 비교

프론트엔드는 식당의 홀처럼 사용자가 보고 누르는 화면이고, 백엔드는 주방처럼 처리·저장을 맡는 부분이에요. 비동기 작업은 접수 번호를 먼저 받고 오래 걸리는 주문은 별도 주방에서 처리하는 방식이에요.

| 선택 | 만들기·유지보수 | 엔진·긴 작업·상태 | 한국어 카드 출력 | 판단 |

| **TypeScript + React/Vite + Express** | 화면/서버 타입 공유 가능. 화면 상태를 작은 부품으로 분리. 패키지 빌드·업데이트 관리 필요 | 공식 TypeScript Agent SDK 직접 연결. 별도 작업 프로세스와 영속 작업표는 직접 구현 | HTML/CSS를 미리보기와 PNG에 재사용하는 구성이 자연스러움 | **추천**: 독립 화면/서버 개발과 통합에 유리 |

### 구체적인 구성 제안과 버전 방침
- 실행 환경: **Node.js 24 LTS 계열** 추천. LTS는 오래 관리되는 공구 규격처럼 안정적으로 유지보수되는 버전이에요. 공식 표는 확인일에 v24를 LTS, v26을 Current로 표시해요. 로컬 PATH의 실제 Node는 **v26.7.0**이라 추천 환경과 달라요. 설치·전환하지 않았어요. [공식-Node]
- 언어/화면: TypeScript, React, Vite. 서버: Express **5 계열**. Express 5 공식 최소 Node는 18 이상이고 Vite 공식 요구는 20.19+/22.12+예요. 추천 Node 24는 문서상 요구 범위에 들어가지만 실제 조합 설치 시험은 미수행이에요.
- 저장: SQLite와 **better-sqlite3**, WAL 및 짧은 트랜잭션. 트랜잭션은 주문과 결제 기록을 함께 확정해 절반만 남는 일을 막는 묶음 처리예요. 네이티브 모듈의 Windows/Node 사전 빌드 조합은 설치 승인 후 확인해야 해요. [공식-DB]
- 출력: 앱 소유 HTML/CSS 카드 템플릿, 로컬 Noto Sans KR, Playwright/Chromium. 글꼴·브라우저 설치가 추가되고 메모리·디스크를 사용하지만 미리보기와 출력 차이를 줄일 수 있어요. [공식-출력, 공식-글꼴]
- 외부 엔진: `@anthropic-ai/claude-agent-sdk`. 공식 SDK는 Python/TypeScript를 지원하며 네이티브 Claude Code 실행 파일을 묶어 제공해요. **SDK와 별도 Claude CLI를 두 앱 엔진으로 함께 구현하는 제안은 아니에요.** SDK 내부 실행 파일은 SDK의 구성 요소예요. [공식-SDK]
- 정확한 모든 패키지 패치 버전은 아직 확정하지 않아요. 승인된 설치·호환 검증 후 잠금 파일에 고정할 대상으로 남겨요. ‘최신이면 모두 호환’이라고 보장하지 않아요.

## 4. 검색·구독·권한 조건

### 검색 방법
1. 후보 수집은 SDK의 `WebSearch`, 선택 후보는 `WebFetch`로 공식 발표·논문·제품 문서부터 확인해요. 내장 웹 도구 존재는 공식 실행 루프 문서로 확인했어요. [공식-검색]
2. 검색어·기준 시각·기간, 원문 URL·접근 시각·게시일/사건일, 주장/검증/불확실성을 앱에 남기는 안이에요. 날짜나 원문 접근에 실패하면 ‘미확인’으로 표시하고 검색 요약만으로 검증 완료를 만들지 않아요.
3. `WebFetch`는 모델로 처리된 결과를 돌려주는 도구이므로 원본 전체가 그대로 보존된다고 가정하지 않아요. 핵심 문장·URL·확인 근거를 구조화하고 제출 전 원문과 대조해야 해요.
4. 실제 뉴스 검색·공급자 API를 이번에는 호출하지 않았어요. 이 작업의 공식 자료 조회 성공이 앱 계정 검색 성공을 증명하지 않아요.

### 구독과 계정 조건(이전 API 추천 대체)
- **본인 기존 구독 OAuth만** 허용해요. `ANTHROPIC_API_KEY`·Console·클라우드/API 청구로 연결하지 않아요. 공식 정책은 ordinary individual Claude Code/Agent SDK 사용과 타인 credential 수집·중계 서비스를 구분해요. 이번은 본인 개인 로컬 수업 실습이며 타인 로그인 UI/중계 서비스는 만들지 않아요. [공식-구독정책]
- 공식 인증 문서상 cloud/gateway/bearer/API key/helper/profile/WIF 등이 구독보다 우선할 수 있고 Console도 OAuth일 수 있어요. **API 키 부재·OAuth 문자열·apiKeySource=none·비용0만으로 구독을 입증할 수 없어요.** 현재 active auth는 미검증이에요. [공식-구독인증]
- 구체적인 **추론 전 fail-closed 검증**은 `📖 인터페이스 계약.md §6`에 있어요. 자식 env allowlist·settingSources=[]·connectors 억제, 남는 managed/global config·profile/gateway를 확인해 동일 자식의 활성 subscription source를 양성 입증해야 해요. documented per-invocation 옵션만 사용하고 확인 불가면 AUTH_MODE_UNKNOWN으로 호출0을 유지해요. host 설정/바이너리 수정·토큰 복사/발급은 하지 않아요.
- 본인이 공식 구독 상태와 **usage credits(이전 extra usage) 비활성화**를 확인한 뒤에만 별도 승인된 제한적 실제 시험을 해요. 공식 도움말에 따르면 크레딧을 켜면 구독 한도 이후 별도 API 요율 청구로 계속될 수 있어 구독 OAuth만으로도 충분하지 않아요(계약 O15). 활성/미확인은 차단하고 설정/충전은 앱이 조작하지 않아요. 구독 만료/한도·검색 비지원/인증 오류는 멈춤과 회복 가능한 오류이며 API/CLI/다른 공급자로 전환하지 않아요. maxTurns/시간·도구 수 제한은 자원 보호일 뿐 청구원 보장이 아니며 maxBudgetUsd를 API 예산 추천으로 쓰지 않아요.
- 선행 API 단가/모델·별도 API 예산 추천은 **미채택 이력으로 폐기**했어요. 아래 공식 출처 표의 API 가격 관련 URL은 선행 조회 이력만이며 현재 구독 청구/권한 증거가 아니에요.
- Antigravity 공개 가격 페이지에는 개인 **$0/월**, 기본 주간 제한이 있어요. 문서는 제한이 작업량과 가용 용량에 따라 달라진다고 설명해요. **이미지 몇 장 무료인지·이 계정의 이미지 권한·추가 비용은 확인하지 못했어요.** 인증 경로별 기능이 같다고 가정하지 않아요. [공식-agy요금]
- 로컬 화면·서버·DB·출력 구성에는 별도 운영 호스팅을 제안하지 않아요. 전기·저장·유지보수·AI 사용 비용은 남아요. `better-sqlite3` MIT, Noto Sans KR OFL 조건을 확인했으며 다른 배포 의존성의 라이선스 확인은 잠금 버전 선정 후 필요해요. 무료 프로그램과 AI 무료 사용을 혼동하지 않아요.

### agy 연동의 정확한 경계
공식 headless 문서는 `agy -p` 자연어 요청과 `text`/`json`/`stream-json` 응답을 설명하고, 도구 문서는 `generate_image`를 이미지 생성/편집 내장 도구로 표시해요. **SDK 도구 문서의 존재만으로 로컬 CLI·이 계정에서 이미지 생성이 된다는 증거는 아니에요.** [공식-agy]

- `agy image generate` 같은 미확인 명령은 만들지 않아요. JSON 출력 옵션은 응답 봉투이며 PNG 형식을 지정하는 옵션이 아니에요.
- 요청한 저장 경로와 실제 반환 경로를 대조하고 작업 폴더 경계·존재·파일 형식·크기·이미지 디코딩을 검사한 뒤 결과 자산으로 등록하는 안이에요.
- 공식 headless 문서상 권한 소프트 거절은 종료 코드 0으로 끝날 수도 있어요. 성공 문장·종료 코드만으로 완료 판정하지 않아요.
- 최소 도구/경로 권한을 설계하고 전면 권한 우회 플래그는 기본안에서 제외해요. 작업 폴더 분리는 보안 샌드박스와 다르며, 외부 원문은 지시가 아닌 자료로 다뤄요.

## 6. 영속 상태와 파일 보관의 추천 구조

영속 저장은 새로고침하거나 앱을 껐다 켜도 주문 장부가 남는 것이에요. 아래는 구성 개요이고 상세 schema/HTTP·파일 계약은 **`📖 인터페이스 계약.md` CN-1 및 `📘 기술 명세서.md`**를 기준으로 해요. 모두 결과 승인 대기 초안이에요.

- **SQLite**: 프로젝트·후보/선택·조사 근거·작업·엔진/세션 ID·질문/답변·카드/결과 버전·승인·요청 중복 기록·오류·진행 이벤트를 보관해요. 메모리 큐·브라우저 저장만을 원장으로 삼지 않아요.
- **로컬 파일**: 프로젝트/작업별 디렉터리에 생성 원본·카드 렌더링·PNG·ZIP·출처/생성 기록을 분리하고 DB에는 자산 식별자·상대 경로·검증 메타데이터를 보관하는 안이에요. 사용자가 임의 경로를 지정해 읽게 하지 않아요.
- **작업 실행**: 서버는 작업 ID를 즉시 반환하고 별도 작업 프로세스가 긴 AI/이미지/출력을 실행해요. 첫 버전은 DB 작업표 기반 제한된 동시 실행과 폴링을 추천해요. 별도 Redis/대규모 큐는 제안하지 않아요. SQLite의 단일 동시 쓰기 한계를 짧은 기록과 순서 제어로 관리해요. [공식-DB]
- **원자적 변경**: 프로젝트 범위의 `requestId`와 입력 지문·저장 응답을 묶어요. 동일 ID/같은 입력은 저장 결과 반환, 다른 입력은 충돌, 진행 중 재요청은 기존 작업 반환. 실제 외부 호출을 분산 시스템 수준으로 정확히 한 번 보장한다고 주장하지 않아요. 중간 단절 후 외부 성공 여부를 모르면 재생성/재과금 가능성을 안내하고 임의 자동 재실행하지 않아요.
- **질문/승인**: `questionId`·버전·프로젝트·현재 상태를 함께 검증해 답변 한 번만 반영해요. `waiting_for_user`는 정상 대기예요. 스토리보드 승인과 최종 결과 승인 모두 현재 버전에 결속하고 수정 시 최종 승인을 해제해요. 비수정 카드의 승인·자산은 보존해요.
- **세션 격리**: 프로젝트별 엔진 ID·명시 세션 ID·작업 디렉터리, 필요한 설정/환경만 전달해요. SDK의 `settingSources` 및 명시적 도구 목록/거절 정책으로 사용자 개인 설정의 예기치 않은 로딩을 막는 안이에요. `allowedTools`만으로 도구 접근을 제한했다고 보지 않아요. [공식-설정]
- **실패/취소/복구**: 인증 필요·검색 실패·이미지 실패·잘못된 답변·취소·중단을 구별해요. 취소 요청 후 앱이 만든 작업·하위 프로세스의 종료/정리 확인 전 성공 취소로 표시하지 않아요. Windows에서는 앱 소유 프로세스 식별·추적·SDK 중단 신호와 자식 정리가 별도 검증 대상이에요. Hermes나 다른 서비스는 취소 대상이 아니에요.
- 서버 재시작 시 살아 있다고 확인하지 못한 실행은 중단으로 전환하고, 저장된 결과/세션에 따라 복구 또는 명시적 재시도를 안내해요. 실행 소유권/임대·작업 시도 버전으로 늦은 결과가 새 결과를 덮지 못하게 하는 안이에요.
- 파일은 임시 생성 → 검증 → 최종 등록 순서로 다뤄 DB/파일 불일치를 복구해요. 승인된 현재 결과만 내보내며 과거 ZIP URL로 미승인 개정판이 노출되지 않게 해요.
- 서버는 `127.0.0.1:8765` 기본, 포트 충돌 대안 안내. 로컬이라도 요청 출처·호스트·변경 요청 보호, 파일 경로 탈출과 외부 URL의 내부망 접근 방어를 후속 설계에 포함해요. 사용자 입력을 셸 문자열로 연결하지 않아요.

**보관 추천**: 향후 승인받은 프로젝트 내부 전용 데이터 위치에 SQLite와 자산을 함께 보관하고 제출 완료까지 자동 삭제하지 않는 안이에요. 정확한 위치·용량·백업/삭제 정책은 사용자 결정이 남아 있어요. 이번에는 그 폴더·DB를 만들지 않았어요.

## 7. 한국어 PNG 렌더링 추천

1. 카드 텍스트·그림 참조·배치 정보를 따로 저장하고 HTML/CSS 카드 템플릿에 넣어요. 모델이 만든 임의 HTML/스크립트를 실행하는 방식은 제외해요.
2. 허용 조건을 확인한 Noto Sans KR을 로컬 자산으로 제공하고 글꼴 로딩·이미지 디코딩 완료를 기다린 뒤 카드 요소를 PNG로 캡처하는 안이에요. Playwright의 요소 캡처는 공식 지원 기능이지만 **이 프로젝트의 한국어 출력은 아직 시험하지 않았어요.**
3. 고정 CSS 크기·출력 배율을 명시하고 실제 디코딩한 PNG가 사용자 선택 1080×1350 또는 1080×1080인지 확인해요. 페이지 전체 스크롤 캡처로 크기를 우연히 맞추지 않아요.
4. 긴 한국어 문장·줄바꿈·출처 URL·누락 글리프·본문 영역 넘침을 자동 점검하고 작은 화면에서 실제 가독성도 별도 검수해요. 글자가 존재한다는 검사만으로 읽기 좋다고 판정하지 않아요.
5. 텍스트만 수정하면 기존 배경 자산을 유지하고 해당 카드만 새로 출력해요. 이미지 수정도 대상 카드만 생성해요. ZIP은 승인 결과 명세의 순서·수량과 일치하고 출처·조사 기준일·도구·생성일·프롬프트·사용 조건 기록을 포함해야 해요.

**중간 통합 제안**: 공통 계약만 먼저 고정한 뒤 화면·서버·출력은 병렬로 진행해요. ① 후보/선택 저장·새로고침 경계가 준비되면 해당 연결만 확인, ② 질문/답변·버전·이중 제출 경계가 준비되면 확인, ③ 스토리보드 승인과 실제 `agy` 한 장이 준비되면 확인, ④ 부분 수정·최종 승인·내보내기를 확인해요. 각 연결 확인 때문에 다른 미완성 화면을 기다리거나 모든 화면을 같은 진도로 묶지 않아요. 끝에는 전체 실흐름과 실패/복구 품질검증, 독립 최종 리뷰를 거쳐요. 실제 카드 생성·연결·해제는 사용자 승인 뒤 default만 해요.

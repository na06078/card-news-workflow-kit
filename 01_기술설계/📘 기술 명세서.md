# 카드뉴스 실습 — 기술 명세서

## 카드 수정 결과 계약과 원본 보존 (2026-10-28, 구현·실모델 복사본 확인)

- 결과 카드 수정은 요청 접수와 실제 적용을 분리한다. app 소유 revisionProtocol2와 strict 범위별 patch/비변경 outcome을 사용하며 모델에 개정·승인·자산·오류 metadata를 맡기지 않는다. 공통 정규화기를 provider와 Store가 재검사하고 worker의 제공자 정리 확인 뒤만 반영한다. 구체 DTO·재시도·파일 소유는 인터페이스 첫 절이 정본이다.
- 접수/정상 비변경/적용 전 실패는 기존 ready/approved 결과·PNG·승인/exports를 보존한다. 실제 변경된 카드만 개정·무효화하고 기존 그림을 재사용해 문구/배치를 렌더한다. 적용 marker로 재시도 위치를 판단하며 선택됐지만 바뀌지 않은 카드도 보존한다.
- 문구·그림·배치의 범위와 원래 지시를 복원한다. 범위 확인은 편집을 열 뿐 자동 재제출/전환하지 않는다. 좁은 검증을 통과한 과거 pending 카드는 명시 renderOnly로 기존 원고 표시만 복구한다. 원래 지시 반영 성공이나 자동 승인으로 꾸미지 않는다.
- dev.2 후속 재시도 보강은 API/worker의 적용 marker 판정을 공유하여 혼합 선택 중 실제 변경 부분집합만 재렌더한다. 적용 전 fresh retry는 기존 ready/approved 콘텐츠 상태를 유지하고 실패는 Run으로 구분한다. 현재 결과·개정/중복/소유권/unknown 확인·active 보호를 유지하며 새 모델 호출이나 과거 marker 재적용으로 복구를 대체하지 않는다. 후속 검증·실행 반영·미커밋/버전 상태는 현재상태 최상단을 따른다.
- 실제 모델 복사본2요청에서 needs_scope(text)/기존결과 보존과 text patch/기존그림/새PNG/저장·새로고침을 확인했다. 새 이미지0/원본문구변경0이며 실제 새 이미지 생성까지 검증한 것은 아니다. 최종 원본 적용·버전 기록·전체 회귀와 보존본 상태는 현재상태를 따른다.

## 리뷰 보강 — 제작 승인·출력 순서·작업자 잠금·초안 보호 (2026-10-27, 구현·격리 확인)

SDK WebFetch 처리 결과의 구조화 HTTP/bytes/URL과 인용을 대조하되 원문 전체 독립 사실 보증이라고 부르지 않는다. 모델 출력은 검수 passed/앱 영수증/변경 전 원고를 정하지 못한다. 기반 계약4PASS, 안전 렌더 원인/기존 정규화 집중17PASS, 실제 Chromium 렌더4PASS/무관4SKIP을 확인했으며 전체 통합 완료는 아직 아니다.

## 공통 수정 요구 — 모든 차단의 원인·해결 행동 표시 (2026-10-26, 구현 기준)

## 최신 구현 — agy 로그인·연결 확인 자동 완료
- 사용자가 ‘계정 정보가 준비되면 웹에 자동 반영하고 이 앱의 인증용 창만 닫기’를 선택했다. login/check는 수동 완료 POST를 요구하지 않고, 현재 작업의 유효한 ready/계정·native 인증 조회·종료 직전 상태를 확인해 완료한다. logout은 기존 명시 확인과 계정 대조를 유지하며 자동 실행하지 않는다.

## 최신 보정 — 실제 statusLine 호출의 Windows 인용 처리
- CMD 기본 argv 전달이 공백·한글을 포함한 따옴표 경로를 잘못 해석하는 실사용 오류를 재현했다. 기존 call 접두사/windowsVerbatimArguments=true 시험만으로 native 경로 성공을 보장한 것은 잘못이었다.
- statusLine 명령은 ASCII PowerShell EncodedCommand로 전달하고 내부에서 경로를 정확히 인용해 기존 Node 수집기를 실행하며 JSON stdin은 UTF-8로 전달한다. 실제 오류를 무시하지 않으며 진행 메시지만 억제한다. 프로젝트 안의 전용 설정만 변경한다.
- 직접 영향6PASS·타입/서버 컴파일exit0 후 실제 agy의 현재 계정 수집/인증 조회/API와 DOM 표시 일치 및 Claude 유지까지7항목PASS, 새 CLI 로그의 Statusline Error0을 확인했다. 현재 두 계정 ID의 실제 표시 검증은 완료됐다. 신규 계정 OAuth 전체·실계정 로그아웃 완료와는 구분한다.

## 2. 구조 — 화면/원장/외부 처리 분리

worker는 오래 걸리는 주문을 처리하는 별도 주방이고, DB는 새로고침 뒤에도 남는 주문 장부예요. 아래 구성은 작은 로컬 실습에서 Redis/클라우드 없이 필수 복구를 지키기 위한 안이에요.

```text
브라우저 React/Vite
  └─ loopback HTTP: 프로젝트/질문/버전/승인·재시도/취소/다운로드
       Express 서버 ───────── SQLite 원장 + 자산 index
          │                              ▲
          └─ 접수 트랜잭션 → jobs ── 별도 worker(lease/CAS)
                                          ├─ Claude Agent SDK: 구독 preflight→조사/편집/질문
                                          ├─ agy adapter: 승인 뒤 지정 카드 실제 그림
                                          ├─ renderer: 고정 HTML/CSS+폰트→PNG
                                          └─ exporter: 승인 manifest→PNG 목록/ZIP/기록
```

| 모듈 | 책임 | 하지 않는 일 |
|---|---|---|
| web UI | topic·기간/후보·질문·계획/카드·승인·부분 실패·다운로드 표시 | credentials/DB 직접 접근, 승인 상태 자체 결정 |
| HTTP service | 입력 검증, CSRF/Origin, 트랜잭션 수락, 상태 조회, 파일 전달 | HTTP 연결에서 모델·이미지·PNG 생성 완료 기다리기 |
| persistence/domain | 상태 전이·versions·request ledger·job/질문·승인·자산 commit | provider 원문을 검증 없이 승인 |
| worker dispatcher | claim/lease/heartbeat, 단계별 실행·답변 polling·취소·복구, CAS commit | ‘성공했을 것’ 가정 재호출, Kanban을 런타임 큐로 사용 |
| Claude adapter | documented SDK 옵션, 구독 인증 검증, 검색/원문·편집/질문 정규화 | API 키/토큰 수집, Bash/파일 임의 변경, 자동 다른 엔진 전환 |
| agy adapter | 독립 argv 프로세스·최소권한·실제 파일 검증·생성기록 | Claude SDK 검색용 대체 엔진, exit0만으로 그림 성공 |
| renderer | 검증된 카드/이미지/폰트·고정 크기→PNG와 검사 | 임의 HTML/JS, 네트워크 fetch, DB/승인 갱신 |
| exporter | 현재 승인 result의 immutable manifest→검증 ZIP/기록 | 승인 우회/과거 파일 URL로 새 결과 제공 |

HTTP·state/event·render 타입은 **`📖 인터페이스 계약.md CN-1`만 단일 기준**이에요. 이 명세에 두 번째 DTO 스키마를 복제하지 않아요. 구현 시 `src/shared/계약.ts`와 `검증.ts`가 해당 계약을 코드로 옮기며 S0가 단독 소유해요.

### 후속 사용자 승인 — 배치 변경과 종료 기록의 연결 누락 보완

- 사용자가 ‘권장 수정안으로 한 번에 진행’을 선택했어요. layout 수정은 같은 입력 재렌더가 아니라, CN-1 후속 보완의 제한된 글자 크기·정렬·위아래 배치 옵션을 실제 저장/렌더 결과까지 전달해요. 원래 카드 모습은 layout 부재 시 유지하고, 대상의 문구·그림과 비대상 카드/승인은 보존해요. 자유 HTML/CSS나 새 편집기는 추가하지 않아요.
- terminal committed 기록은 backend Store.commit이 최종 상태/결과·event와 같은 DB 트랜잭션에 저장해요. 완료 뒤 journal 추가나 완료 전 선기록으로 우회하지 않으며, 저장 실패 시 함께 롤백해요. worker는 그 원자 commit 성공을 기다려요. 자세한 필드·검증은 CN-1의 ‘layout 실제 반영과 완료 기록 원자 저장’이 단일 기준이에요.
- 이번 보완 동안 W1의 한정 쓰기 권한을 관련 shared/provider/render/backend/worker 및 직접 영향 테스트까지 확대해요. 원본·프론트·전역 런타임·의존성은 변경하지 않고 실제 AI/검색/agy 호출 금지는 유지해요. 기존 I2 선행 관계도 유지해요.

## 6. 작업·질문·재시작·취소

### 접수와 실행
- CN-1 §3의 requestId 원장+payload 비교+CAS+job/event 저장은 하나의 transaction. 외부 effect exactly-once는 주장하지 않음.
- worker boot UUID와 lease/fencing으로 claim. 짧은 DB polling, 전역 외부 작업 동시 1 추천(최종 사용자 승인 전 제안). 여러 project 질문 대기는 project별 저장, 별도 SDK Query/세션/컨텍스트로 혼선 방지.
- queued 시작시 attempt별 디렉터리와 invocation journal을 먼저 저장: prepared→started→output_observed→validated→committed. 중간 단계에는 run/attempt/파일 예상명/해시를 기록하되 credentials/raw provider stdout 저장 금지.
- 단계마다 base version/lease/취소 flag 확인. 추론/이미지 끝난 뒤 검증하는 사이 취소됐다면 결과 채택 금지. 외부 성공했으나 DB commit 실패는 unknown이 될 수 있음, 임의 재생성 금지.

### 질문 대기
- callback은 worker가 소유. 질문/tool-use/session/run/version을 DB에 저장한 뒤 waiting_for_user event. HTTP는 대기 Promise를 보유하지 않음.
- answers는 DB에 단 한 번 저장. worker polling→callback updatedInput으로 전달→running. 전달 직전 죽었는지 직후 죽었는지 판별 불가하면 unknown/복구 검증 필요. ‘delivered’ flag 하나로 SDK가 받았다고 증명하지 않음.
- 질문 대기 중 SDK query는 살아 있고 새 추론은 하지 않아야 하며 lease heartbeat는 유지. worker 프로세스/메모리를 무한정 유지 못하면 deferred 방식이 아니라 CN-1의 interrupted+명시 복구로 정직하게 처리. SDK defer는 후속 검증 전 채택하지 않음.

### 재시작과 재시도
- HTTP만 재시작했고 worker lease가 살아 있으면 상태를 그대로 재조회. 부팅했다는 이유만으로 모든 job을 interrupted로 바꾸지 않음.
- lease 만료+owner 동일 생존 확인 불가인 경우 fencing 증가하고 interrupted. 살아 있을 수 있는 이전 worker의 외부 호출을 고려해 새 외부 호출 자동 시작 금지. stale worker의 late commit은 fencing으로 거절.
- worker도 죽은 질문은 DB 질문/선택/답변 유지, callback은 복구되지 않음. 저장 sessionId/cwd 기반 명시 resume은 설치 버전의 pending tool 실제 시험을 통과해야 허용. 불가하면 SESSION_RECOVERY_UNVERIFIED 및 사용자가 확인할 재시도 선택. session이 없을 때 다른 project나 latest로 연결하지 않음.
- retry는 새 runId, 실패한 phase/card만 대상으로 기존 유효 자산/승인 재사용. local render/export는 파일 hash 검증으로 안전 재사용 가능. provider started 이후 외부 결과 불명은 EXTERNAL_OUTCOME_UNKNOWN·confirmUnknownOutcome 필요. 인증/권한 실패는 먼저 해결 확인, 자동 API/다른 엔진 fallback 없음.

### 취소
- 요청→cancel_requested DB, worker가 각 실행 소유자에게 취소를 요청해요. SDK/agy 실행 소유자가 자신이 만든 **특정 PID/생성시각/실행파일/부모 관계와 하위 실행 종료**를 확인하고 CN-1 후속 보완의 CleanupReport를 반환해요. worker는 그 결과와 렌더의 browser.close 완료 경계를 기다려 상태를 확정하며, 다른 담당자의 private 프로세스를 직접 검색/종료하지 않아요. PID 재사용 방어, 이름/wildcard kill·Hermes/다른 서비스 종료 금지는 유지해요.
- Windows 하위 프로세스 전체 추적/정리 확인이 성공해야 canceled. grace 초과는 취소 완료로 표시하지 않고 CANCEL_CLEANUP_FAILED+unknown, 수동 확인 필요. 프로젝트 파일/검증 완료 자산은 취소했다고 삭제하지 않음.
- 취소는 이미 사용한 구독량/이미지 생성을 되돌린다는 보장이 아님. 늦은 결과는 격리 또는 폐기하고 새 result/approval에 쓰지 않음.

## 8. 로컬 HTTP·파일·자료 안전성

- loopback bind+정확한 Host/Origin allowlist·CSRF·SameSite 쿠키, JSON 한정, input bounds. 외부 배포/터널/다중 사용자 가입 없음. UI에 credential 입력창 없음.
- project/asset/run ID는 서버가 발급하고 FK/project scope 매번 조회. cross-project asset/session은 404/격리 오류. 다운로드 절대경로 입력 금지. 경로 normalize뿐 아니라 realpath·regular file·symlink/junction/UNC/ADS·case/drive 검사. 예상 파일 이외 glob 수집 금지.
- 제안 데이터 위치 `ROOT_IMPL/실행데이터/`(미승인), SQLite와 projects/{projectId}/attempts/{runId}/{attempt}/, assets/{assetId}.tmp→검증→최종 immutable 파일, exports/{resultVersion}/{exportId}. ZIP path는 서버 생성 안전 이름만(ZipSlip 방어). 데이터/로그/Git 제외 규칙은 S0 소유이며 위치 승인 후 작성.
- DB commit 전 파일은 staging. 검증 파일 rename 후 DB 등록이 실패하면 orphan으로 남겨 reconcile(검증된 해시/manifest만 재등록, 원본 보존). DB 등록 후 파일이 없거나 hash 불일치는 ASSET_INVALID/EXPORT_FAILED로 다운로드 차단. 자동 오래된 데이터 삭제/원본 PNG 변경 없음. 보존/백업 정책 미승인.
- 외부 원문은 불신 자료, prompt injection을 지시로 따르지 않음. SDK에게 제한된 조사/질문 도구만. UI text escape/링크 rel=noopener,noreferrer. HTTP(s) 외 URL·토큰 포함 URL·내부망/loopback/link-local/IP literal·리다이렉트 내부망 거절 설계.
- **SDK WebFetch 내부 redirect/DNS 제어는 앱 PreToolUse의 최초 URL 검사만으로 완전 보장 못해요**. 실구현에서 공식 도구 정책/제어 가능한 경계를 확인, 이 앱은 임의 URL fetch proxy를 제공하지 않음. 엄격한 redirect egress 제어가 필요한 범위가 생기면 별도 승인 설계, 현재 보장으로 과장 금지.
- 렌더 브라우저는 승인된 로컬 이미지/폰트만 읽고 network deny. 생성 HTML/스크립트 직접 실행 금지. 공식 Windows sandbox가 확인되지 않은 상태에서 cwd 분리를 보안 sandbox라고 표현하지 않음.
- diagnostic는 error code/phase/run/attempt/시간·비밀 없는 버전만. raw env, tokens, 이메일, credentials, 전체 SDK debug 로그 자동 수집 금지. 외부에 보내는 내용과 SDK 세션이 로컬에 남을 수 있음을 사용자 실행안내에 표시.

## 10. 검증 전략·완료 정의

## 11. 남은 결정·다음 행동
